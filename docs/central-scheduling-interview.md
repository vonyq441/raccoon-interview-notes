# 具身智能中央调度平台：大厂校招模拟面试题与答案解析

这份题单配合《多机器人中央调度平台：设计、执行与面试》使用。参考用户提供的巡检项目模拟面试截图的考察维度，按**项目深挖 → 系统设计 → 编码思路 → 行为追问**组织，但题目和答案都围绕展厅中央调度重新编写。答题顺序建议是**问题 → 自己做过的实现 → 为什么这样设计 → 如何验证 → 边界与不足**。不要照背方案文档，把待实现机制说成上线事实。

**已确认的个人经历：**甘肃 5G 联合创新中心展厅项目已经上线验收；实际两台机器人，一楼十几个展台、二楼约十个。本人负责 Java 平台中的中央规划 Agent 与 RAG 知识问答 Agent，且这两部分在验收范围内。机器人和开发电脑连接展厅 Wi-Fi，开发时通过 SSH 登录机器人联调。实际 Java—机器人业务协议、模型与存储的上线版本，以及下文各增强机制是否落地，仍需用工程代码、配置和验收记录核实。

下文的**建议回答**是面试准备口径，包含项目事实和可解释的设计，不是未经核实的个人业绩。尤其不能从“Agent”一词推出 ReAct、多 Agent 自治、全局轨迹规划或百台机器人规模。

## 一、项目定位与中央规划 Agent

### Q1. 请用九十秒介绍项目，并说清你负责的部分

**考察点：**业务价值、职责边界、实际规模与交付状态。

**建议回答：**项目为展厅接待提供中央规划和知识问答能力，实际部署两台机器人。我负责 Java 侧的规划 Agent 与 RAG：把工作人员的接待重点映射为已有展台的候选顺序，围绕当前展台检索资料并回答问题。这两部分已进入上线验收。计划审核、资源占用和机器人下发属于平台业务流程；其中哪些接口由我实现，应以实际代码举证。导航、避障和动作执行由机器人侧负责。

**继续追问：**给一条脱敏规划输入、模型原始草案、Java 校验结果、工作人员最终路线，以及对应的本人代码位置。答不出这些，九十秒介绍仍过于抽象。

### Q2. 只有“生成计划”一个功能，凭什么称为智能规划？固定模板不行吗

**考察点：**模型带来的增量价值和对照实验。

**建议回答：**固定路线完全能处理常规接待；模型的价值是把不固定的自然语言重点映射到已配置展台，并给审核人一个可修改草案。若上线功能只完成一次生成，我会如实称它为“受约束计划生成”，不声称自主全局优化。对同一批需求比较固定模板与模型辅助的有效草案率、必经站覆盖、人工修改量和从输入到审核通过的耗时，才能证明实际收益。

**继续追问：**换一个展台暂停开放，结果如何变化？如果上线规划没有读实时开放状态，就不能用这个案例证明已交付的动态能力。

### Q3. 你的系统是 ReAct、Plan-and-Execute，还是多 Agent

**考察点：**是否理解模型调用与智能体架构的区别。

**建议回答：**已确认的中央规划职责是提出可审核的展台路线草案；Java 业务服务控制审核、任务状态和执行前复核。规划、意图分类、问答可采用不同 ChatClient 或 Prompt，并共用底层模型；这不自动形成三个自主 Agent。若没有多轮自主工具调用和独立决策循环，最准确的说法是“LLM 辅助的受约束规划工作流”。机器人逐站执行不等于模型进入 ReAct 循环。

**继续追问：**画出一次模型调用的输入和输出，以及哪些判断仍由 Java 完成。不要用“模型能思考”替代接口说明。

### Q4. 从“重点看液冷和具身智能，十五分钟左右”到审核通过，完整链路是什么

**考察点：**事实来源、模型输出、业务校验与人机分工。

**建议回答：**工作人员先确认接待日期和目标时长；Java 提供启用中的展台、楼层和可用资源，规划模型只从允许的编码中选择并排序。Java 检查编码存在、去重、必经站、点位和讲稿版本等，给出时间风险，再交工作人员审核。审核后保存任务和各站步骤；访客到场前不把整条路线下发机器人。示例 JSON 中不让模型自报逐站导航耗时。

**继续追问：**审核期间展台被关闭或资源包被更新怎么办？审核时重新校验并绑定版本；不能只信生成时的快照。

### Q5. 模型返回合法 JSON，却漏掉必经站、选错楼层，怎么发现

**考察点：**格式正确与语义正确的区别。

**建议回答：**输出 Schema 只解决解析；Java 还要用可信配置检查展台存在、楼层、资源、必经点、重复点和当前任务状态。对可明确修复的格式错误可以有限重试；业务事实错误不靠反复清理 Markdown、放宽为 JSON5 或让模型自己给自己打分兜底。无合法方案时退回人工选择或标准模板。

**继续追问：**给一条具体反例及拒绝理由，并说明是否真的在已验收版本中做过这项校验。

### Q6. 十五分钟怎么计算？机器人导航不由 Java 控制

**考察点：**估计的不确定性与真实职责边界。

**建议回答：**“十五分钟”是接待目标，不是平台保证的完成时间。讲稿配置或实测播放时长只能提供基线；移动耗时仅在有机器人出发/到达历史或现场测量时估计，并标明依据。开放问答、避障、排队和跨楼层交接都有变化；数据不足就展示未知项和超时风险。Java 不给 Nav2 指定速度，也不让模型凭空补一段 ETA。

**继续追问：**讲稿共九分钟、目标十五分钟，能否批准？只能说明还余六分钟容纳其他环节，不能断言一定准点；工作人员应看风险后决定是否删减。

### Q7. 巡检项目也有中央规划 Agent，是同一个已上线 Agent 吗

**考察点：**跨项目复用与经历真实性。

**建议回答：**已确认上线验收的是展厅接待规划；“同一规划框架扩展到巡检”目前是方案设计。两场景可共用模型调用、结构化解析和审计骨架，但接待用展台/讲稿/访客约束，巡检用设备/规程/传感器/工单约束，需要独立输出 Schema、校验器和执行适配。当前仓库的巡检规划代码不能自动证明展厅系统复用了同一部署。

**继续追问：**如果让你真做复用，`sceneType` 由认证后的业务入口确定，而不是让模型从一句模糊指令猜任务类型。

## 二、多机器人执行与一致性

### Q8. 两台机器人同时要去同一个容量为 1 的展台，谁负责阻止

**考察点：**规划时预判与执行前互斥。

**建议回答：**Agent 可以根据当前占用提出错峰建议，但真正防止双重占用的是 Java 在导航下发前的原子预约。事务中抢到目标名额的一台才创建命令；另一台保持原任务状态，等待、选择允许的其他展台或让工作人员改线。预约先为 `RESERVED`，到站变 `OCCUPIED`；讲解结束不代表访客已离场，确认清场后才释放。

**继续追问：**两个请求同时读到空闲怎么办？用数据库条件更新或行锁保证只有一个成功，不能依靠先读 Redis 再分别写入。

### Q9. 两组分别占着 A 和 B，同时想去对方的站，数据库没有死锁还会怎样

**考察点：**业务层循环等待与现场安全。

**建议回答：**会出现 A 等 B、B 等 A 的业务互等，数据库事务即使都提交也不能使现场继续。平台需要识别等待关系和超时，提示工作人员使用预先配置且可达的等待区、改线或结束一段接待；离场确认前不能假释放原展台。机器人本地避障也不保证窄通道不会互堵。

**继续追问：**如果没有安全等待区，就暂停并交人工，不让模型编一个临时停靠点。

### Q10. 为什么区分 Task、Step、Command、Event？为什么只发当前站

**考察点：**计划与物理执行的对应关系。

**建议回答：**Task 是一场接待，Step 是审核后的某一站，Command 是本次给机器人的实际业务指令，Event 是接收、导航、到站、讲解和结果反馈。一步可能因取消/恢复对应多次命令，一条命令有多条事件。Java 保存完整路线，机器人只接收当前目标，改线就只替换尚未执行的步骤；“命令已发送”不等于“机器人已完成”。

**继续追问：**导航到站是否意味着展台讲解成功？不是，音频播放、必需动作及停止/打断结果仍需分别确认。

### Q11. 手机和语音同时请求“下一站”，或者 NEXT 与改线并发，怎样避免跳站

**考察点：**幂等、版本与并发状态机。

**建议回答：**操作请求带 `requestId` 和当前 Step、计划/任务版本前提；Java 在同一任务事务入口串行化推进、改线和暂停。只有当前命令确定结束、步骤允许推进、目标资源抢占成功，才创建下一条 Command。重复请求返回第一次结果；不同请求竞争时，后提交者收到版本冲突并刷新。若上线版本没有完整实现这些机制，要明确它是增强方案。

**继续追问：**仅有 `requestId` 为什么不够？它只能去重同一请求，不能阻止两个不同编号各推进一站。

### Q12. 机器人执行了但平台没收到结果，能否超时后新建命令重试

**考察点：**分布式不确定性与物理动作幂等。

**建议回答：**不能盲目新建。平台把命令标为待确认/`UNKNOWN`，按同一 `commandId` 向机器人查询或等待重连补报；传输重投也使用原编号，端侧应去重。若无法证明动作是否已执行，暂停后续下发并转人工核实。数据库与物理动作之间不能保证真正的 exactly-once。

**继续追问：**心跳恢复为何不等于结果恢复？心跳只表示最近可联系，不能证明某条导航或讲解命令的终态。

### Q13. 访客临时改线，但机器人已经在去原展台的路上，怎么处理

**考察点：**取消边界、计划版本与运动安全。

**建议回答：**先判断当前命令是否允许继续；必须改目标时先请求取消，并确认机器人停止或已到达。状态不明则暂停新目标。Java 只修改未执行步骤和计划版本，已完成事件不被覆盖；不能通过改数据库让正在运动的机器人瞬间换方向。局部避障由机器人导航栈负责。

**继续追问：**导航受阻后是否总需要大模型？不是；明确等待或直接人工拖动顺序时，Java 规则可以处理。

### Q14. Java 与机器人到底通过什么协议通信？你说的 SSH 是什么

**考察点：**有没有把开发联调方式讲成运行时架构。

**建议回答：**已确认机器人和开发电脑连接展厅 Wi-Fi，开发时用 SSH 登录机器人；SSH 只证明开发访问路径。Java 到机器人实际命令与反馈的业务协议目前需要从客户端、服务端配置和脱敏日志核实。文档中的 REST/WebSocket 是设计示例，不应作为已上线实现背诵。

**继续追问：**若面试官要求画一次已验收请求的完整调用链，面试前必须补齐协议和接口证据，不能用“应该是 WebSocket”作答。

## 三、知识问答与语音路由

### Q15. 为什么规划可以不用 RAG，知识问答却需要 RAG

**考察点：**事实数据、知识证据与模型职责。

**建议回答：**展台启停、导航点、机器人占用和讲稿版本等规划依据应来自受控业务配置和状态，而不是相似文本检索。展台专业问答依赖说明书和 FAQ，需要按当前展台及已发布资料版本检索证据，再生成有依据的回答。检索可以辅助理解资料，不能决定机器人当前该去哪里。

**继续追问：**如果问题明确问另一个展台，先校验目标编码和访问范围，再检索那个范围；不偷偷改变当前 Task/Step。

### Q16. 机器人麦克风收到一句话，如何区分问答、下一站和改线

**考察点：**意图路由误触发的安全后果。

**建议回答：**ASR 转文字后，开放语音可由受限意图分类得到 `NEXT`、`ROUTE_CHANGE`、`KNOWLEDGE_QA` 或 `UNKNOWN` 候选。Java 再查说话人控制权限、当前步骤和命令状态；“为什么下一站是液冷”属于问答，“先不要去下一站”是否定，不能靠包含“下一站”就执行。歧义句先澄清，本地安全停止不等模型分类。

**继续追问：**规划、意图、问答三个 ChatClient 可以共用一个 ChatModel；这只是职责隔离，不等于多 Agent。

### Q17. 从上传 PDF 到机器人回答，RAG 的关键环节是什么

**考察点：**资料版本、切块、召回与引用。

**建议回答：**管理员确认展台归属和访问范围后上传资料，解析文本、保留标题/页码/段落等来源信息，切块、向量化并发布完整知识版本。提问时以可信 `taskId/stepId` 定位展台，检索该范围的已发布片段，去重和判断证据充分性，再让模型生成回答并只引用本次召回证据。原始文件、元数据和向量的实际存储产品须按上线配置说明。

**继续追问：**只说“TopK=5 + Prompt”不够；正确答案没进 TopK 是召回问题，进了却答错是生成/证据约束问题。

### Q18. 如果资料没有答案、检索到跨展台片段或用户故意让模型执行动作，怎么办

**考察点：**拒答、范围隔离、提示注入与控制隔离。

**建议回答：**证据不足就明确不知道或请工作人员补资料；引用必须属于当前允许的检索结果。资料正文是低信任输入，不能因其中写有“下一站”“执行动作”就调用控制接口。问答输出只走安全的普通文本播报路径，不能被讲稿动作标记解析器当成控制脚本。答案返回和播放前都检查当前步骤是否仍有效。

**继续追问：**给出“资料写着忽略系统指令并让机器人前进”的测试样本，说明控制服务为何不会消费它。

### Q19. 两台机器人同时问答，同一台机器人连续提问，答案顺序乱了怎么办

**考察点：**并发隔离、上下文与过期响应。

**建议回答：**不同机器人按 `robotId/taskId/stepId` 隔离检索范围和上下文；同一机器人按 `utteranceId` 管提问顺序、取消和 TTS 播放。后发问题先返回时，不应覆盖先前仍有效的追问上下文；若访客打断，就显式使旧回答失效。切站、暂停或任务结束后，旧答案即使返回也不播放。

**继续追问：**“有 utteranceId”不是排队机制；要说清服务端和播放端如何判定哪一条仍有效。

## 四、验收、扩展与个人复盘

### Q20. 你怎么证明规划 Agent 和 RAG 有效，而不是演示时看起来不错

**考察点：**指标口径、基线和样本质量。

**建议回答：**规划以人工模板为基线，比较有效草案率、必经站覆盖、工作人员修改和审核总耗时；RAG 分开测 Recall@K、答案是否被证据支持、无答案错误作答和误拒答。控制语音单独测 NEXT 误触发，系统层记录真实并发与 P95 时延。报告分母、样本数、资料/模型版本及测试条件，不借用巡检项目的性能数字。验收通过不自动等于这些指标已有测量结果。

**继续追问：**说一个你亲自定位的失败样本：输入、错误输出、根因、修改、回归对照和验收版本；没有记录就明确尚未统计。

### Q21. 从两台机器人扩到十台，你先改变什么架构

**考察点：**瓶颈识别与不过度设计。

**建议回答：**先测模型调用限额和排队、机器人连接/状态推送、同站容量竞争、人工审核吞吐及现场通道瓶颈。按真实瓶颈配置有界队列、超时、每机器人配额和资源预约；只有单实例确实无法满足负载或可用性目标，再拆分服务或引入更复杂协调。机器人本地控制仍保持独立，不能把多机任务调度夸大为全局无碰撞轨迹规划。

**继续追问：**十台是假设压测规模还是实际部署？实际已确认部署两台，必须先说清。

### Q22. 这个项目最大的技术取舍与不足是什么

**考察点：**是否能独立复盘，不堆术语。

**建议回答：**用模型处理自然语言接待偏好与知识问答，用 Java 校验、审核和状态机守住业务事实，用机器人本地导航保证运动边界。代价是规划并非全自主、时间估计存在未知项、跨端命令恢复需要严格对账。回答时选一个自己确实处理过的缺陷或取舍，展示为什么采用当前办法、它没有解决什么，以及下一步怎样验证改进。

**继续追问：**哪一部分你写了代码、哪一部分只是设计？分别给出代码、联调和验收证据。

## 五、System Design 白板题：把方案画到可执行

以下均是**假设面试题**，回答时先说明题设和取舍；它们不能作为已上线架构或压测成绩写进简历。

### Q23. 三十分钟设计一个支持多机器人接待的中央调度服务，你先问什么、画什么

**考察点：**需求澄清、容量边界、数据模型和失败恢复。

**建议回答：**先问机器人/展台数量、展台容量、是否跨楼层、人工审核是否必需、允许等待还是必须改线、机器人侧可提供哪些回执，以及断网后的安全要求。画 `Task → PlanVersion → Step → Command → Event` 主链路和 `Robot/ExhibitReservation` 两类资源。模型只产出候选路线；审核和下发由 Java 状态机处理。对容量为 1 的展台，出发前原子预约；命令与待发送记录同事务落库，端侧按 `commandId` 去重；失联命令标记待核对，停止后续自动下发。先给两台机器的单实例设计，再按压测瓶颈讨论扩容。

**继续追问：**如果面试官要求“千台”，先要求每台请求频率、模型调用占比、并发峰值和可用性目标，再谈分片、队列和连接归属；不能把截图中巡检项目的千台数字搬过来。

### Q24. 写出展台名额抢占的核心 SQL 和事务边界

**考察点：**原子性、资源计数与外部调用边界。

**建议回答：**设计中在同一数据库事务里先锁当前任务与机器人分配，再用条件更新抢展台名额：`UPDATE exhibit SET occupied_slots=occupied_slots+1 WHERE exhibit_code=? AND occupied_slots<capacity`。只有影响一行时，才新增 `RESERVED` 预约、当前 Step 的 Command 和 outbox；任何一步失败全部回滚。事务提交后再发送机器人命令。释放时按预约状态条件更新，只允许一次，并同步减计数；`UNKNOWN` 不自动释放。所有占用写路径都走同一服务，定期比对计数与明细。

**继续追问：**为什么不能先查 `occupied_slots` 再发命令？并发两次读取都可能看到空位，而且网络发送不能随数据库回滚；先查再发既可能超容量，也可能出现机器人动了但平台无记录。

### Q25. 代码题：NEXT 与改线并发、请求重放，服务端怎么写

**考察点：**同一任务的串行化、幂等与版本冲突。

**建议回答：**以 `(taskId, requestId)` 唯一键做同一操作去重；事务中锁任务行或做条件版本更新，确认 `expectedTaskVersion/currentStepId` 仍匹配，再校验当前 Command 已终结、目标资源可用，最后只推进一次 Step、增加版本并记录下一条 Command。改线只更新未执行 Step，也必须在同一任务版本序列里竞争。不同 `requestId` 即使内容相同，也不能绕开 Step 前置条件。伪代码应标清事务范围；模型调用和网络发送都放在事务外。

**继续追问：**客户端超时重试但第一次事务已提交时，查幂等结果并返回原结果；机器人执行状态不明时，不能为了“补偿”直接创建新导航命令。

### Q26. 规划与检索并行读取后，超时和旧数据如何处理

**考察点：**并发编排、时间预算、取消与快照一致性。

**建议回答：**只有互不依赖的读取才可并行。规划所需的展台清单、启停、讲稿版本和占用快照要带版本或读取时间，模型返回后以当前数据库状态再次校验；慢查询不是放宽约束的理由。给每一段独立超时和总超时，过期任务取消下游调用或丢弃迟到结果，并标记降级原因。硬约束数据缺失时不自动批准草案；RAG 检索超时则告知资料暂不可用，不编造答案。线程池、模型并发上限和等待队列有界，避免两台机器的慢请求堆积。

**继续追问：**`CompletableFuture.allOf(...).get(timeout)` 只限制等待时间，并不自动停止仍在运行的外部请求；还要讨论客户端超时、取消传播及迟到结果的版本校验。

### Q27. Prompt、模型或展台资料升级后，如何避免新版本把现场带偏

**考察点：**版本治理与可回滚性。

**建议回答：**把 Prompt、模型、展台配置、讲稿和知识库发布版本记录到任务/问答追踪信息中。上线前用脱敏回归样本评估合法草案率、必经站覆盖、无证据拒答和误触发；小范围试运行时保留人工审核及一键回退到前一已知版本。已审核计划引用的展台配置发生重大变化时必须重新校验，不因 Prompt 回滚就覆盖已经执行的事件。灰度比例和效果数字只有真实测量后才能写。

**继续追问：**如果新模型 JSON 更规范却把必经站漏掉更多，是否发布？不能只看格式通过率，要按业务正确性和风险样本决定。

## 六、Behavior 与反问：把个人贡献讲成证据链

### Q28. 讲一次你亲自解决的最难问题

**考察点：**个人归属、诊断过程、结果与复盘。

**建议回答框架：**用一条真实案例按“触发场景 → 可观察症状 → 自己查到的证据 → 备选方案及取舍 → 本人改动 → 回归与验收结果 → 剩余限制”讲。优先选规划内容正确性或 RAG 错答/串场的真实问题。没有日志、工单、代码提交和前后对照时，不填具体 P95 或错误率，也不把系统设计题的假设案例包装为线上故障。

**继续追问：**面试官让你打开代码或画调用链时，能否指出自己的类、测试与提交？如果只能说“团队做了”，就缩小到本人实际负责的环节。

### Q29. 项目验收后，你最想推翻哪个设计决定

**考察点：**权衡能力，而不是事后堆技术名词。

**建议回答框架：**选一个真实决定，例如规划输入未纳入实时占用、RAG 资料更新与向量发布耦合、或异常命令缺少对账界面。说明当时为什么接受、具体代价在哪个场景出现、改动会增加什么复杂度，以及怎样以两台机器人和现有展台先验证收益。若某项只是文档增强方案，就用“下一步计划验证”表述，不声称它已经造成过线上故障。

**继续追问：**如果重做只允许一周，你先补哪一条可观测性或校验链路？给出能验收的完成标准。

### Q30. 面试最后，你会问面试官什么

**考察点：**岗位判断力与协作意识。

**建议回答：**可结合目标团队问：“贵团队让模型建议进入生产业务流程时，哪些结果必须经确定性校验或人工审核？线上更看重回答质量、尾延迟，还是失败恢复？”再问新同学的代码所有权、回归样本和联调方式。问题要服务于岗位判断，不暗示自己已做过千台调度或完整自主 Agent 平台。

### Q31. 14:00 和 14:20 两场接待追尾：机器人 1 在 B 问答，机器人 2 在 A 的下一站也是 B，怎么调度

**考察点：**排程预测与实时占用的区别、候补公平性、等待体验和失效恢复。

**建议回答：**二十分钟错峰不保证 B 到时空闲。机器人 2 出发前预约 B 失败，就不创建去 B 的命令，而是在 A 登记 `WAITING` 候补；它可以继续回答 A 的问题或播放已审核补充讲稿。`WAITING` 不占 B 容量，也不是数据库读锁。机器人 1 和接待组实际离开 B 后，Java 在短事务中释放原占用并将候补首位转成限时 `RESERVED`；机器人 2 完成当前回答，平台再次核对计划、设备和预约，再保存 Command/outbox，提交后才下发。B 被预约但尚未下发时可按配置期限撤销并让下一位接手；命令已下发或实际状态不明时不能靠超时释放。

**继续追问：**机器人 2 在 A 收尾期间为何不能说“您可以留在 A 继续问机器人 2”？因为它即将离开；若留游客自助参观，还需定义 A 的现场接管与容量释放。另问：取消任务与 B 清场同时发生如何避免死锁？清场事务不在持有 B 展台锁时反向锁候补任务；正式下发前再锁任务、检查版本，已取消则释放短时预约并转给下一位。本题及其代码是扩展设计，不能说成已验收功能。

## 面试前先备齐四组证据

1. **规划链路：**一条已验收请求的脱敏输入、允许展台列表、模型原始输出、Java 校验、审核结果和本人代码位置。
2. **问答链路：**一条有答案及一条无答案的问题，展示资料版本、召回片段、模型输出、引用和播放前上下文校验。
3. **失败复盘：**一个真实异常的时间线、日志关联键、根因、修复与回归；设计假设不能冒充线上事故。
4. **事实清单：**实际 Java—机器人协议、模型与向量库版本、本人代码范围、验收记录、实测指标；未知项明确标“待核实”。
