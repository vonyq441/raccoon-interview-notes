# AI Agent 智能体面试题学习文档

> 题库来源：[面试鸭：AI Agent 智能体面试题](https://www.mianshiya.com/bank/2052284728362414082)。本文包含题库中的全部 50 道题，每题标题均可跳转到原文。答案为便于学习和面试表达而重新整理，并非网页原文的逐字复制。

## 一、怎么学习

建议依次学习：

1. **Agent 基础与运行循环**：知道 Agent 到底是什么、怎样完成任务。
2. **工具、上下文与记忆**：知道 Agent 怎样获得能力、保存信息并控制上下文。
3. **MCP**：知道 Agent 怎样标准化接入工具和数据。
4. **多 Agent 与 A2A**：知道多个 Agent 怎样分工与通信。
5. **生产级设计**：知道怎样保证安全、稳定、可观测和可评估。
6. **框架与前沿应用**：了解 Manus、ADK、AutoGPT 和 Computer Use。

标记说明：

- **核心题**：建议能够用自己的话完整回答。
- **速记题**：与前文重复，记住区别和跳转关系即可。
- **扩展题**：理解用途，不需要背框架源码。

## 二、Agent 基础与运行循环

<a id="q1"></a>
### 1. [什么是 AI Agent？它和直接调用大模型 API 有什么区别？](https://www.mianshiya.com/bank/2052284728362414082/question/2052284768782921729)

**核心题。** 普通大模型 API 通常是一次输入、一次输出；Agent 会在大模型外增加工具、记忆、状态和循环控制。它能够根据目标决定下一步行动，读取工具结果后继续判断，直到完成任务或触发退出条件。可以速记为：`Agent = LLM + Tools + Memory + Loop`。

<a id="q2"></a>
### 2. [AI Agent 的核心组件有哪些？感知、决策、执行、记忆各自有什么作用？](https://www.mianshiya.com/bank/2052284728362414082/question/2052284768199913474)

**核心题。** 感知负责接收用户输入、文件或环境状态；决策通常由大模型完成任务理解、规划和工具选择；执行负责调用真实工具；记忆保存当前任务状态和历史经验。工程上还要增加编排器、安全控制、日志与评估模块，否则难以稳定运行。

<a id="q3"></a>
### 3. [什么是 Agent Loop？一个典型循环包含哪些步骤？](https://www.mianshiya.com/bank/2052284728362414082/question/2052284763179331586)

**核心题。** 一个典型循环是：接收目标 → 分析当前状态 → 选择工具或直接回答 → 执行工具 → 记录观察结果 → 判断是否继续。循环不是无限运行，必须有完成、失败、用户取消、超时和最大步数等退出条件。

<a id="q4"></a>
### 4. [ReAct 推理范式是什么？它如何让 Agent 更可靠地完成任务？](https://www.mianshiya.com/bank/2052284728362414082/question/2052284765498781698)

**核心题。** ReAct 将推理和行动交替进行：模型根据现有信息决定行动，系统执行工具并返回 Observation，模型再根据真实结果调整下一步。它比一次性生成完整答案更可靠，因为中间步骤可以获得外部证据并及时纠偏。

<a id="q5"></a>
### 5. [什么是 Reflexion？它和 ReAct 有什么区别？](https://www.mianshiya.com/bank/2052284728362414082/question/2052284762055258114)

**核心题。** ReAct 关注“思考—行动—观察”的即时循环；Reflexion 会在任务失败或结果较差后进行复盘，形成错误原因和改进建议，再用于下一次尝试。简单说，ReAct 是边做边调整，Reflexion 是做完或失败后总结经验。

<a id="q6"></a>
### 6. [Agent 系统如何设计终止条件并避免死循环？](https://www.mianshiya.com/bank/2052284728362414082/question/2052284762629877762)

**核心题。** 正常结束可由结构化完成状态或专门的结束工具触发；异常结束包括最大步数、总超时、费用预算、连续失败和用户取消。系统还应记录最近的工具名与参数，发现重复调用时停止或切换策略，不能只相信模型自己说“任务完成”。

<a id="q7"></a>
### 7. [什么是大模型 Agent？它与传统 AI 系统有什么不同？](https://www.mianshiya.com/bank/2052284728362414082/question/1916425038718943233)

**速记题。** 参见[第 1 题](#q1)。传统 AI 多用于固定的分类、预测或规则流程；大模型 Agent 能理解自然语言目标，并动态规划和调用工具，但自主性越高，可控性也越难保证。

<a id="q8"></a>
### 8. [LLM Agent 的基本架构有哪些组成部分？](https://www.mianshiya.com/bank/2052284728362414082/question/1916425039008350210)

**速记题。** 参见[第 2 题](#q2)。面试时可按“交互入口—编排器—模型—工具—记忆—安全与观测”六部分回答，比只说感知、决策、执行更加工程化。

<a id="q9"></a>
### 9. [LLM Agent 常见功能有哪些？](https://www.mianshiya.com/bank/2052284728362414082/question/1916425039243231233)

**速记题。** 常见功能包括任务理解与拆解、知识检索、工具调用、代码或文件处理、记忆、结果校验和多 Agent 协作。功能不是越多越好，应由实际场景决定，例如机器人中央 Agent 更需要任务规划、设备查询和状态跟踪。

<a id="q10"></a>
### 10. [Agent 智能体的工作过程是怎样的？](https://www.mianshiya.com/bank/2052284728362414082/question/1916425039528443905)

**速记题。** 参见[第 3 题](#q3)。可以概括为“理解目标—获取上下文—制定下一步—调用工具—观察结果—完成或继续”。

<a id="q11"></a>
### 11. [ReAct 是什么？说说它的原理](https://www.mianshiya.com/bank/2052284728362414082/question/1915710074900160513)

**速记题。** 参见[第 4 题](#q4)。面试时不要声称必须输出模型完整思维链，生产系统通常只保存工具调用、状态变化和必要的决策摘要。

<a id="q12"></a>
### 12. [Agent 死循环问题遇到过吗？如何解决？](https://www.mianshiya.com/bank/2052284728362414082/question/1935997509803618306)

**速记题。** 参见[第 6 题](#q6)。项目回答要补充真实例子，例如模型重复搜索同一文件时，通过工具参数指纹去重、最大重试次数和人工确认终止循环。

## 三、工具调用、上下文与记忆

<a id="q13"></a>
### 13. [什么是 Tool Calling？它的基本流程是什么？](https://www.mianshiya.com/bank/2052284728362414082/question/2052284775367979010)

**核心题。** 应用先向模型提供工具名称、说明和参数结构；模型返回希望调用的工具和参数；应用完成权限与参数校验后执行工具；再把结果交给模型生成回答或继续决策。模型只是提出调用请求，真正执行和安全控制都在应用端。

<a id="q14"></a>
### 14. [什么是 Agent 的上下文窗口？为什么它是核心约束？](https://www.mianshiya.com/bank/2052284728362414082/question/2052284774025801729)

**核心题。** 上下文窗口是一次模型调用能够接收和生成的 Token 总量。系统提示、历史消息、工具定义、检索文档和工具结果都会占用它。超过上限会调用失败，接近上限也会增加费用、延迟和信息干扰，因此上下文管理直接影响 Agent 能连续完成多长的任务。

<a id="q15"></a>
### 15. [工具调用返回超大结果时怎么处理？](https://www.mianshiya.com/bank/2052284728362414082/question/2052284769391095809)

**核心题。** 不把全部内容直接塞回模型。优先让工具支持过滤、分页和字段选择；大结果写入文件或对象存储，只返回摘要、来源位置和句柄；模型需要细节时再精准读取。对于代码仓库，可返回文件路径和行号，而不是整仓代码。

<a id="q16"></a>
### 16. [对话历史超出上下文窗口时，有哪些压缩策略？](https://www.mianshiya.com/bank/2052284728362414082/question/2052284770259316738)

**核心题。** 常见策略有滑动窗口、历史摘要、按相关性检索旧记忆、结构化保存任务状态，以及把大内容外置后按需读取。滑动窗口简单但可能丢信息；摘要省 Token 但可能失真；向量检索适合长期历史但存在漏召回。实践中通常组合使用。

<a id="q17"></a>
### 17. [AI Agent 的记忆有哪些类型？短期和长期记忆怎么实现？](https://www.mianshiya.com/bank/2052284728362414082/question/2052284774613004289)

**核心题。** 短期记忆保存当前会话和任务状态，可使用内存、Redis 或数据库中的会话记录；长期记忆保存跨会话仍有价值的事实、偏好和经验，可使用关系数据库、文档库或向量库。完整聊天历史和真正提供给模型的记忆应分开管理。

<a id="q18"></a>
### 18. [如何让 AI Agent 具备长期记忆能力？有哪些存储和检索方案？](https://www.mianshiya.com/bank/2052284728362414082/question/2052284764907384833)

**核心题。** 先从交互中提取值得长期保存的信息，再带上用户、时间、类型和权限等元信息写入数据库。明确事实适合关系数据库，非结构化经历适合向量库。使用前按用户和权限过滤，再按关键词、语义相似度或时间进行检索，并提供删除和更新能力。

<a id="q19"></a>
### 19. [如何设计 Agent 的工具权限控制？](https://www.mianshiya.com/bank/2052284728362414082/question/2052284775955181570)

**核心题。** 按用户、Agent、任务和环境建立工具白名单，并对参数范围、目标资源和调用频率做校验。只读查询可以自动执行；写数据、发送消息、控制设备等操作应要求更高权限，必要时人工确认。密钥不进入 Prompt，敏感工具还要有幂等、审计和撤销机制。

<a id="q20"></a>
### 20. [如何利用 Spring AI 实现 Tool Calling？](https://www.mianshiya.com/bank/2052284728362414082/question/1929742306206928897)

**速记题。** 原理参见[第 13 题](#q13)。Spring AI 可用 `@Tool`、ToolCallback 或 ToolCallbackProvider 暴露 Java 方法，再注册给 `ChatClient`；业务方法内部仍需执行鉴权、参数校验、超时和异常转换。

<a id="q21"></a>
### 21. [LLM Agent 如何进行动态 API 调用？](https://www.mianshiya.com/bank/2052284728362414082/question/1916425040195338241)

**速记题。** 参见[第 13 题](#q13)。系统把允许调用的 API 封装成工具，模型根据工具说明选择名称和参数，应用验证后调用真实 API。不能让模型直接拼任意 URL 或 SQL。

<a id="q22"></a>
### 22. [在大模型应用中，通常如何实现长短期记忆？](https://www.mianshiya.com/bank/2052284728362414082/question/1916410560665989122)

**速记题。** 参见[第 17 题](#q17)。短期记忆服务当前任务，长期记忆服务跨会话信息；二者都应有容量、过期时间、用户隔离和隐私删除策略。

<a id="q23"></a>
### 23. [如何让 LLM Agent 具备长期记忆能力？](https://www.mianshiya.com/bank/2052284728362414082/question/1916425039918514178)

**速记题。** 参见[第 18 题](#q18)。长期记忆不是把所有聊天永久塞给模型，而是“提取—保存—检索—更新”的独立流程。

## 四、MCP：连接工具和数据

<a id="q24"></a>
### 24. [MCP 协议是什么？它解决了什么问题？](https://www.mianshiya.com/bank/2052284728362414082/question/2052284767310721026)

**核心题。** MCP 是 AI 应用连接外部工具、资源和 Prompt 的标准协议。没有 MCP 时，每个 Agent 都要为每项服务编写专用适配；有了 MCP，Server 用统一方式暴露能力，Host 通过 Client 连接。它解决的是接入标准化问题，不会自动解决业务权限和安全问题。

<a id="q25"></a>
### 25. [MCP 架构有哪些核心组件？Server 和 Client 分别负责什么？](https://www.mianshiya.com/bank/2052284728362414082/question/2052284766648020994)

**核心题。** Host 是运行模型和管理安全策略的 AI 应用；每个 Client 负责与一个 MCP Server 建立会话；Server 暴露 Tools、Resources 和 Prompts。Client 负责能力发现、协议通信和结果转换，Server 负责具体业务能力，但最终是否允许调用由 Host 控制。

<a id="q26"></a>
### 26. [MCP 的工作流程是什么？](https://www.mianshiya.com/bank/2052284728362414082/question/1914241826055909377)

**核心题。** Client 与 Server 建立连接并完成初始化，协商协议和能力；Client 获取工具或资源列表；模型选择工具后，Host 通过 Client 发出调用；Server 执行业务并返回结构化结果。整个过程还需要处理超时、错误、取消和连接生命周期。

<a id="q27"></a>
### 27. [MCP 协议的安全性设计包含哪些层面？](https://www.mianshiya.com/bank/2052284728362414082/question/1914241826546642946)

**核心题。** 主要包括连接认证、用户授权、最小权限、工具与参数白名单、传输加密、敏感数据保护、调用审计和人工确认。远程 Server 的工具描述和返回内容都属于不可信输入，不能因为接入 MCP 就默认可信。

<a id="q28"></a>
### 28. [如何将已有应用转换成 MCP 服务？](https://www.mianshiya.com/bank/2052284728362414082/question/1914241826789912577)

**核心题。** 不必重写原业务，通常在外面增加 MCP 适配层：选择适合给 Agent 使用的接口，定义清晰的工具名、说明和参数 Schema，调用原有 Service，再把结果转换成简洁的结构化内容。同时补上认证、权限、超时、幂等和审计。

<a id="q29"></a>
### 29. [Function Calling 和 MCP 有什么区别？](https://www.mianshiya.com/bank/2052284728362414082/question/2052284773392461825)

**核心题。** Function Calling 是模型表达“要调用哪个函数、参数是什么”的能力；MCP 是 AI 应用与外部服务之间发现和调用工具的标准协议。前者更靠近模型，后者更靠近系统集成。少量本地函数直接注册更简单；跨应用、跨语言或工具较多时 MCP 更便于复用。

## 五、多 Agent 与 A2A

<a id="q30"></a>
### 30. [什么是 A2A？它和 MCP 有什么区别？](https://www.mianshiya.com/bank/2052284728362414082/question/2052284766136315906)

**核心题。** A2A 用于独立 Agent 之间的能力发现、任务委托、状态更新和结果交付；MCP 用于 Agent 或 AI 应用连接工具和数据。可以简单理解为：MCP 解决“Agent 用什么工具”，A2A 解决“Agent 找哪个 Agent 合作”。

<a id="q31"></a>
### 31. [A2A 中的 Agent Card 是什么？](https://www.mianshiya.com/bank/2052284728362414082/question/2052284761493221377)

**核心题。** Agent Card 是 Agent 对外公开的能力说明，通常包含名称、地址、版本、技能、认证要求以及支持的输入输出形式。调用方先读取 Card，再判断该 Agent 是否适合当前任务。它类似 Agent 的电子名片，但不能代替运行时鉴权。

<a id="q32"></a>
### 32. [多 Agent 协作有哪些常见编排模式？](https://www.mianshiya.com/bank/2052284728362414082/question/2052284772746539009)

**核心题。** 常见模式包括主管 Agent 委派专家、顺序流水线、并行执行后汇总、路由选择，以及多个 Agent 讨论。任务边界清晰时用顺序或并行；需要动态选择能力时用主管模式；高风险业务不适合无限自由讨论，应由确定性流程控制关键节点。

<a id="q33"></a>
### 33. [子 Agent 模式有什么优势和挑战？](https://www.mianshiya.com/bank/2052284728362414082/question/2052284776634658817)

**核心题。** 子 Agent 可以隔离上下文、并行完成专业子任务，让主 Agent 聚焦目标和最终决策。挑战是重复工作、成本上升、结果冲突和上下文丢失。父 Agent 委派时要明确目标、输入范围、输出格式、工具权限、超时和完成标准。

<a id="q34"></a>
### 34. [A2A 的核心架构和主要组件有哪些？](https://www.mianshiya.com/bank/2052284728362414082/question/1916425042913247233)

**核心题。** 调用方是 Client Agent，被调用方是 Remote Agent；Agent Card 用于能力发现，Message 用于沟通，Task 表示可跟踪的工作，Artifact 表示交付结果。长任务还需要状态更新、取消和异步通知。

<a id="q35"></a>
### 35. [A2A 协议有哪五大设计原则？](https://www.mianshiya.com/bank/2052284728362414082/question/1916425043148128258)

**扩展题。** 可概括为：充分支持 Agent 自主协作、复用 Web 等现有标准、安全默认开启、支持长时间任务，以及支持文本之外的多种模态。面试重点不是死背顺序，而是解释为什么 Agent 通信不能只当作一次普通 REST 调用。

<a id="q36"></a>
### 36. [A2A 的工作原理是怎样的？](https://www.mianshiya.com/bank/2052284728362414082/question/1916425043395592193)

**核心题。** 调用方先通过 Agent Card 了解远程 Agent，再发送消息或创建任务；远程 Agent 自主执行，并通过任务状态和消息持续反馈；完成后返回 Artifact。调用方不需要知道远程 Agent 内部使用什么模型或框架。

<a id="q37"></a>
### 37. [A2A 的工作流程是怎样的？](https://www.mianshiya.com/bank/2052284728362414082/question/1916425043643056130)

**速记题。** 参见[第 36 题](#q36)。速记为：发现 Agent → 协商能力和认证 → 提交任务 → 跟踪状态 → 接收结果 → 结束或继续交互。

<a id="q38"></a>
### 38. [A2A 与 MCP 的关系是怎样的？](https://www.mianshiya.com/bank/2052284728362414082/question/1916432330246103042)

**速记题。** 参见[第 30 题](#q30)。二者不是替代关系：A2A 负责 Agent 间协作，某个 Agent 在完成任务时仍可通过 MCP 调用数据库、搜索或业务工具。

<a id="q39"></a>
### 39. [MCP 和 A2A 如何协同？请设计一个同时使用两者的系统](https://www.mianshiya.com/bank/2052284728362414082/question/2052284770817159170)

## 八、补充面试题：Agent Harness 与运行模式

### 补1：你当下对 AI Agent 的理解是什么？为什么说 `Agent = Model + Harness`？

**回答：** Model 负责理解、推理和生成下一步行动，Harness 是模型外部支撑任务持续运行的工程系统，负责准备上下文、提供工具、保存状态、执行循环并实施安全控制。因此 Agent 不是单独一个大模型，而是“模型的推理能力 + Harness 的执行和控制能力”。没有 Harness，模型通常只能完成一次输入、一次输出；有了 Harness，模型才能观察环境、调用工具、根据结果继续行动并最终交付任务。

### 补2：Harness 通常包含哪些核心组件？

**回答：** Harness 没有唯一的官方分层，可以从工程职责概括为：

1. **上下文管理**：选择系统提示、历史消息、任务状态和检索资料，控制提供给模型的信息。
2. **工具系统**：描述、注册和执行工具，并处理参数校验、超时、重试与结果转换。
3. **状态与记忆**：保存当前任务进度、短期会话信息以及可跨任务复用的长期经验。
4. **Loop 与编排控制**：反复执行“调用模型—执行行动—返回观察结果”，并判断继续或结束。
5. **执行环境**：提供文件系统、终端、浏览器、代码解释器等真实工作空间。
6. **安全与约束**：通过权限、沙箱、白名单、预算、人工确认和最大步数限制危险行为。
7. **可观测性**：记录模型输入输出、工具调用、Token、耗时、异常和任务轨迹，便于排错与评估。

多 Agent 调度可以建立在这些能力之上，但不是每个 Harness 必须具备的基础组件。

### 补3：Agent Loop 属不属于 Harness？

**回答：** 取决于对 Harness 的定义。采用广义定义时，模型之外负责 Agent 运行的系统都属于 Harness，Loop 控制器自然包含在内；采用狭义定义时，Harness 可能只指工具、上下文、文件和沙箱等执行环境，而 Loop 由上层 Agent Runtime 负责。面试时应先说明自己的口径。工程上更实用的说法是：Loop 与 Harness 密切相关，不必争论名称边界，重点是系统必须负责循环、退出、超时、重复检测和状态恢复，不能让模型无限运行。

### 补4：常见的 Agent Loop 模式有哪些？

**回答：** 常见模式可以按自主程度从低到高理解：

1. **固定工作流（Workflow）**：步骤由代码预先规定，模型只处理某些节点。稳定、可审计，适合审批、设备控制等高风险场景。
2. **Tool Calling Loop**：模型选择工具，系统执行后把结果返回模型，直到模型直接回答或触发结束条件。适合步骤不多的查询和操作任务。
3. **ReAct**：按照“分析当前情况—采取行动—观察结果”循环，边执行边调整，适合搜索、排障和环境信息不断变化的任务。
4. **Plan-and-Execute**：先形成整体计划，再由执行器逐项完成；环境变化时可以重新规划。适合目标较复杂、步骤之间有依赖的任务。
5. **Reflection/Reflexion**：执行后增加检查和反思环节，根据错误原因修改方案并重试，适合代码生成和结果可验证的任务。
6. **多 Agent 协作循环**：主 Agent 拆解和派发任务，专业 Agent 分别执行，主 Agent 汇总、校验或继续补充。适合可并行或需要不同专业能力的复杂任务。

实际项目可以混合使用。例如多机器人平台用 Agent 生成计划，但任务审核、状态流转和指令下发采用固定工作流；AW 工具则采用“初步建模—定向补证—REUSE/CREATE—结果校验”的受控循环。

### 补5：Function Calling、Tool Calling、MCP 和 CLI 分别是什么？

**回答：**

- **Function Calling**：模型按给定 Schema 输出要调用的函数名和参数，本质是结构化表达调用意图；函数仍由应用程序执行。
- **Tool Calling**：含义通常更宽，工具可以是本地函数、HTTP API、MCP Tool、数据库查询或 CLI 命令。Function Calling 是实现 Tool Calling 的常见方式。
- **MCP**：AI 应用连接工具、资源和 Prompt 的标准协议，解决能力发现、参数描述和跨应用复用问题。
- **CLI**：通过命令行参数启动程序的交互入口，例如 `git status`。它是真实能力的一种调用方式，不是专门为 Agent 设计的协议。

四者可以同时出现：模型通过 Function Calling 选择一个工具，Harness 调用 MCP Server 暴露的 Tool，而这个 Tool 内部再执行某个 CLI 命令。

### 补6：MCP 和 CLI 有什么区别？应该怎样选择？

**回答：** CLI 面向终端用户和脚本，通常通过命令、参数、退出码和标准输出交互；MCP 面向 AI Host，提供统一的能力发现、参数 Schema、结构化调用和结果返回。CLI 简单、成熟，适合已有命令行工具；MCP 更适合工具较多、需要被不同 Agent 发现和复用的场景。两者不是替代关系，可以用 MCP Server 对 CLI 进行封装，但必须限制可执行命令和参数，不能把任意 Shell 权限直接交给模型。

以机器人项目为例，`bot_mind` 通过 MCP 暴露 `navigate_to`、`stop_robot` 等明确工具，上层 Agent 不需要拼接 ROS2 或 Shell 命令；开发人员调试时仍然可以通过 CLI 脚本调用同一能力。

### 补7：Harness 中的文件系统、上下文、记忆和沙箱有什么区别？

**回答：** 文件系统是保存和读取真实文件的持久化工作空间；上下文是某一轮实际发送给模型的有限信息；记忆是系统从历史任务中保存并按需取回的信息；沙箱是限制代码、命令和文件操作范围的隔离环境。文件存在磁盘上不等于已经进入模型上下文，记忆保存在数据库中也需要经过检索才能进入上下文。沙箱则负责保证即使模型产生错误操作，也不能越权访问宿主机、敏感文件或危险网络资源。

### 补8：多 Agent 是 Harness 的基础组件吗？

**回答：** 不一定。单 Agent 只要具备模型、上下文、工具、状态和循环控制就可以完成任务。多 Agent 是复杂任务下的一种高级编排方式，用于专业分工、上下文隔离和并行处理，但会带来通信成本、结果冲突、重复工作和状态一致性问题。只有任务确实可以拆分，或者单 Agent 的上下文与工具集合过于复杂时，才有必要引入多 Agent。

### 补9：项目中的 Prompt 是怎样设计和优化的？

**回答：** Prompt 优化不是简单增加文字，而是把任务边界变成稳定、可验证的输入输出契约。通常包含角色与目标、可信输入、允许的工具、禁止事项、决策规则、输出 Schema 和少量边界示例。规划、问答和结果校验应使用不同 Prompt，避免一个提示词承担所有职责。优化时建立失败样本集，观察是意图识别、工具选择、参数生成还是结果表达出错，再针对具体问题调整 Prompt，并使用固定样本回归，而不是只凭单次效果判断。

机器人规划 Prompt 只允许从工具返回的展台、waypoint 和机器人中选择，并输出结构化路线；问答 Prompt 只允许依据检索证据回答，证据不足时明确拒答；真正的资源存在性、任务状态和设备安全仍由 Java 代码校验。

### 补10：怎样降低大模型幻觉？

**回答：** 幻觉不能只靠一句“不要编造”解决，需要分层控制：

1. **输入层**：使用 RAG 或工具提供真实、最新的业务证据，并过滤权限、版本和业务范围。
2. **生成层**：明确要求仅依据证据回答，关键输出使用 JSON Schema，证据不足时返回 `INSUFFICIENT_EVIDENCE`。
3. **执行层**：模型输出只作为建议或调用意图，ID、参数、状态和权限由业务代码再次校验，不能直接控制数据库或设备。
4. **结果层**：检查引用是否真实存在、答案中的关键数字是否能在证据中找到，必要时增加校验模型或人工确认。
5. **评估层**：维护包含有答案、无答案、冲突资料和越权问题的固定测试集，持续评估忠实度、拒答率和工具调用正确率。

### 补11：一个真实的 RAG 系统包含哪些流程？

**回答：** 离线阶段包括文档上传、格式解析、清洗、按标题和语义分块、补充元数据、Embedding、入库和抽样验证；在线阶段包括问题理解或改写、权限与业务范围过滤、向量或关键词召回、去重与重排、证据组装、模型生成、引用返回和结果评估。RAG 不只是“向量检索 TopK”，文档质量、元数据、拒答阈值、引用和评测往往比单纯更换向量数据库更重要。

### 补12：RAG 和知识图谱有什么区别？什么时候结合使用？

**回答：** RAG 主要从非结构化文档中寻找与问题相关的证据，擅长回答“手册中怎么描述、某个概念是什么”；知识图谱用实体和关系表达确定连接，擅长回答“设备属于哪个区域、故障会影响哪些部件、两个对象经过几跳关联”。两者结合时，可以先通过图关系限定实体和范围，再检索相关文档，或者将图查询结果与文本片段一起交给模型。

知识图谱不是 RAG 项目的标配。数据量小、关系简单时，关系数据库的外键和关联表已经足够；只有真实存在复杂多跳关系、关系频繁变化或图遍历需求时，再考虑 Neo4j/GraphRAG，不能为了技术名词强行引入。

### 补13：怎样评估 RAG，而不是只看回答感觉？

**回答：** 先准备带标准证据和参考答案的真实问题集，将检索与生成分开评估。检索侧关注 Recall@K、MRR、过滤准确性和是否命中正确版本；生成侧关注答案正确性、对证据的忠实度、引用准确性和无答案拒答率；工程侧还要记录 P95 延迟、Token、成本和失败率。修改分块、Embedding、TopK、Prompt 或重排策略后，都用同一批样本回归比较。

### 补14：项目使用什么 Embedding 模型？为什么选择它？

**回答：** 展厅中文资料可以选择本地部署的 `moka-ai/m3e-base`。它面向中英文语义检索，适合中文讲解稿、FAQ 和产品资料；模型规模适中，能够在内网运行，避免把展厅资料发送到公网。模型选择不能只看榜单，应使用项目问题集比较 Recall@K、查询延迟和资源占用。需要注意，`m3e-base` 输出的是 **768 维**向量，不是 384 维。

### 补15：为什么不能说“M3E-base 生成 384 维向量”？

**回答：** 向量维度由模型结构决定，不是为了节省空间随意填写的数据库参数。`m3e-base` 的隐藏维度是 768，因此输出向量和 pgvector 字段都应使用 768 维。Spring AI 默认 ONNX 示例模型 `all-MiniLM-L6-v2` 才是 384 维。除非增加经过验证的降维步骤，否则不能把 768 维结果直接存进 `vector(384)`。

### 补16：本地 M3E 模型怎样被 Spring AI 调用？

**回答：** 先将 Hugging Face 上的 M3E 模型离线导出为 ONNX，并把 `model.onnx` 和 `tokenizer.json` 部署到内网服务器。Java 引入 Spring AI Transformers Starter，由 `TransformersEmbeddingModel` 在 JVM 中通过 ONNX Runtime 加载模型；业务层只依赖统一的 `EmbeddingModel` 接口。这样不需要为 Embedding 单独维护 Python HTTP 服务。

核心配置可以概括为：

```yaml
spring:
  ai:
    model:
      embedding: transformers
    embedding:
      transformer:
        onnx:
          model-uri: file:/opt/models/m3e-base/model.onnx
        tokenizer:
          uri: file:/opt/models/m3e-base/tokenizer.json
          options:
            padding: true
```

如果模型由 Ollama 提供，则改用 `OllamaEmbeddingModel`；如果由独立的 OpenAI 兼容服务提供，则可以使用相应的远程 Embedding 实现。无论底层怎样部署，业务代码都应面向 `EmbeddingModel`。

### 补17：Spring AI 中哪些组件共同完成向量入库和查询？

**回答：** `EmbeddingModel` 负责把文本转换为向量，`VectorStore` 负责保存和检索文档，使用 PostgreSQL 时具体实现是 `PgVectorStore`。入库时业务把文本和元数据封装成 `Document`，调用 `vectorStore.add(documents)`，`PgVectorStore` 会使用注入的 `EmbeddingModel` 生成向量并写入数据库；查询时调用 `similaritySearch(SearchRequest)`，系统先对问题生成同模型向量，再执行相似度搜索和元数据过滤。

### 补18：Embedding 模型更换后，原来的向量还能继续使用吗？

**回答：** 通常不能。不同模型的维度和语义空间不同，即使维度恰好相同，两个模型生成的坐标也不具有可比性。更换模型后应创建新索引或新表，对全部 Chunk 重新 Embedding，完成离线评测和灰度切换后再删除旧向量。生产中要记录 `embeddingModel、embeddingVersion、dimension`，避免新旧向量混用。

### 补19：向量维度越高，检索效果一定越好吗？

**回答：** 不一定。更高维度可以表达更多特征，但也会增加存储、索引内存和距离计算成本，最终效果主要由模型训练质量和业务数据决定。应在同一批真实问题上比较召回率、延迟和资源消耗，而不是只根据维度选择模型。对规模较小的展厅知识库，768 维是可以接受的，但必须通过评测证明模型适合中文展厅资料。

### 补20：真实项目中怎样定义和使用 EmbeddingModel？

**回答：** `EmbeddingModel` 是 Spring AI 的统一接口，不能直接 `new EmbeddingModel()`；`TransformersEmbeddingModel`、`OllamaEmbeddingModel` 等是具体实现。生产代码通常有两种配置方式：

1. 引入 Transformers Starter，并通过 `spring.ai.embedding.transformer.*` 配置 ONNX 与 tokenizer 路径，由 Spring Boot 自动装配 `EmbeddingModel`；
2. 在配置类中创建 `TransformersEmbeddingModel`，设置本地模型和 tokenizer，再以 `EmbeddingModel` 类型注册为 `@Bean`，适合多个模型或自定义参数的情况。

业务 Service 只注入 `EmbeddingModel` 或直接注入使用它的 `VectorStore`，不依赖具体实现。对象注册为 Spring Bean 时，Spring 会执行初始化生命周期，一般不手动调用 `afterPropertiesSet()`；只有脱离 Spring 容器直接 `new TransformersEmbeddingModel()` 时，才需要配置完成后手动调用它。

```java
@Bean
EmbeddingModel m3eEmbeddingModel() {
    TransformersEmbeddingModel model = new TransformersEmbeddingModel();
    model.setModelResource("file:/opt/models/m3e-base/model.onnx");
    model.setTokenizerResource("file:/opt/models/m3e-base/tokenizer.json");
    model.setTokenizerOptions(Map.of("padding", "true"));
    return model;
}
```

`PgVectorStore` 构造时注入这个 `EmbeddingModel`。调用 `vectorStore.add(documents)` 和 `similaritySearch(...)` 时，VectorStore 会分别完成文档和查询文本的向量化，业务代码通常不必手动调用 `embed()`。
